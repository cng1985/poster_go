# 部署

## 路径

| 路径 | 用途 |
| --- | --- |
| `/opt/poster/bin/poster` | 程序 |
| `/opt/poster/configs` | 配置，升级时保留 |
| `/var/lib/poster` | SQLite、上传文件 |

安装脚本创建系统用户 `poster`，写入 systemd 单元，并以 `--profile pro --data-dir /var/lib/poster` 启动。第一次 `enable --now`，之后 `restart`。

升级前先停止服务，把旧二进制复制为 `poster.prev`，再替换程序。配置和数据目录不会被覆盖。数据库迁移如果向前改了结构，不能假定换回旧二进制就能恢复数据。

## 日志与健康

日志写到标准输出，交给 journald。访问日志包含时间、级别、请求标识、用户、路由模板、耗时和业务码，不记录令牌、密码和提示词正文。

`/health/live` 不检查数据库和模型。`/health/ready` 要求迁移完成并且数据库在 2 秒内可 ping。模型故障不会把存活检查打成失败。

关闭时先取消就绪，再按停止超时排空 HTTP，最后关闭数据库。

## 备份

SQLite 默认 `journal_mode=DELETE`。在线备份要使用 SQLite 备份接口，不能在进程开着时只复制 `app.db` 却漏掉后续如果改成 WAL 的 `-wal` 文件。离线备份需要先停止服务。

本仓库没有自动备份任务，也没有做过恢复演练。生产启用前需要单独定 RPO、RTO 和恢复检查。

## 限流

登录失败、注册、生成和分析的频率限制都在进程内存里，多实例不共享，键数量超过 10000 会清空。这只防止单机上的误操作，不是全局限流。

## 模型密钥

生产把 `APP_AI_API_KEY` 配进 systemd 的 `Environment=` 或凭据文件，不要写进配置模板。配置了密钥后，生成和分析会把用户提示词和海报文案发到该供应商。
